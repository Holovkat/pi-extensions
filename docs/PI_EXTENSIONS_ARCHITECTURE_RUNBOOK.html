pi-extensions Architecture and Environment Runbook

A single self-contained reference for how the pi-extensions multi-agent workflow suite is structured: the two-phase lifecycle extensions, the pif Flutter shell and its hub, the council/comms agent-to-agent layer, environment placement, ports, and quality gates.

Branch: remediation/wave-2-epic-170 · Commit cc9d1e0f · Updated 2026-08-23

01

Executive Summary

What this project is

pi-extensions is a collection of custom extensions for the pi coding agent CLI. The extensions orchestrate multi-agent workflows that cover the full software development lifecycle: interactive requirements discovery, sprint-based implementation with compliance gates, GitHub-native planning, agent-to-agent messaging, and — most recently — a native macOS agentic IDE shell.

The two-phase lifecycle

The core workflow runs in two phases. Phase 1 — requirements discovery: the req-qa extension interviews the user one question at a time, consults specialist agents (requirements, technical, UX, scenario analysts) on demand, and only after explicit user sign-off produces a PRD plus an implementation checklist, published as GitHub issues. Phase 2 — sprint development: the dev-pipeline extension takes those issues and implements them epic by epic, in either a lean Fast Track mode (build → evaluate → fix → UAT) or a thorough 3-Wave mode (foundations council → prototype → review → dev sprint), both ending at explicit UAT approval gates before any merge.

pif — the Flutter macOS shell

pif turns pi into a desktop agentic IDE. A Node-side hub extension (extensions/pif.ts) owns sessions, widgets, layout, and model configuration; a Flutter macOS app renders it through a docking shell; the two talk over a token-authenticated WebSocket bus on port 31415. Child agent sessions run as pi RPC subprocesses and are persisted per-project in SQLite so reopened projects recall their transcripts.

council / coms layer

Beneath the pipelines sits a peer-to-peer messaging layer: coms.ts for same-machine Unix-socket messaging between pi agents, and council.ts for networked request/response councils over an HTTP/SSE hub (scripts/council-server.ts, default port 48201). Pipelines use these substrates for multi-model architect councils and reviews.

This runbook describes the working tree, not a release.

It was generated against commit cc9d1e0f on branch remediation/wave-2-epic-170 (epic #170 remediation wave 2). Paths, ports, and env vars were verified by grepping the source at that commit; later commits may drift.

System Map

Two-phase lifecycle overview

Adapted from docs/diagrams/development-lifecycle.mmd. Requirements discovery ends with published GitHub issues; sprint development consumes them epic by epic.

Dual-mode pipeline

/pipeline-start defaults to Fast Track; --multiwave selects the 3-Wave mode. Both auto-chain across epics and converge on a Playwright-run UAT gate with explicit approve/reject. Adapted from docs/diagrams/dual-mode-pipeline-architecture.mmd.

Agent subprocess execution and steering

All pipeline agents run as pi RPC child processes driven over stdin/stdout; a TCP control socket on port 3142 forwards steering commands from the web dashboard into a running agent's stdin. Adapted from docs/diagrams/agent-subprocess-execution.mmd and agent-steering-control-flow.mmd.

pif hub ↔ Flutter shell ↔ RPC child sessions

The hub owns all state; the Dart renderer is stateless and requests authoritative snapshots. Every connection must present the per-launch token (written to .pi/pif/token, mode 0600). Child sessions are separate pi --mode rpc processes whose transcripts persist to SQLite.

Council topology

Agents register with a project-scoped hub over HTTP/SSE; senders pick recipients by metadata rather than fixed topology. The first local agent can auto-start the embedded hub.

05

Extension Architectures

req-qa — requirements discovery state machine

extensions/req-qa.ts (~1670 lines) drives an interview loop with explicit phases. Specialist agents are defined as markdown files in agents/req-qa/ (frontmatter name/description/tools + system prompt body) and spawned as fresh pi subprocesses per consultation. Two tools: consult_specialist and generate_artifacts (blocked until user sign-off).

dev-pipeline — dual-mode sprint development

extensions/dev-pipeline.ts implements both modes described in section 03. Key mechanisms verified in source and docs:

  • RPC children: every agent spawns pi --mode rpc --no-extensions --no-skills with stdin JSON prompts and stdout JSON event streams; session files are reused so an agent keeps context across calls within a phase.
  • Watchdog fix escalation: fix attempts get a timeout of roughly 10 minutes plus 5 minutes per depth; if the agent yields, the analyst decides decompose / simplify / deprecate / skip and posts learnings back to the GitHub issue so the next depth starts smarter.
  • Compliance scoring: tasks score below 95% loop back for targeted fixes; Fast Track allows up to 5 depths, 3-Wave caps retries per task.
  • Steering: the web dashboard's control socket (port 3142) registers running agents and forwards steer messages onto their stdin.
  • Gates: nothing merges without the UAT approval step (/pipeline-approve vs /pipeline-reject).

pi-blueprint — planning cockpit

extensions/pi-blueprint.ts shares the interview/consultation skeleton with req-qa but targets GitHub-backed planning: transcript search, alignment checks against issue history, issue rebuilds, asset sync (/blueprint-sync-assets mirrors agents/pi-blueprint/ and skills/pi-blueprint/ into a project-local .pi runtime), and a web mirror dashboard (bin/blueprint-dashboard-web). It reads MCP wiring from .mcp.json / .factory/mcp.json.

pi-toolshed — card workbench

extensions/pi-toolshed.ts is a card/workspace shell: frontier packets (freezing active workspace state), workspace presets, quick actions, generated cards for workflows and MCP apps, inline adapters (calculator, GitHub project kanban, generic), and a web surface (bin/toolshed-dashboard-web). Commands include /toolshed-workspace, /toolshed-freeze, /toolshed-packets.

06

pif Architecture

Roles

Three cooperating processes form pif:

  • Hub (extensions/pif.ts): the single authority. Owns sessions (host + children), widget registry/catalog/layout, model list and providers, health state, and supervises both the WebSocket bus and the Flutter shell process.
  • Shell (pif/ Flutter macOS app): stateless renderer. Reconnects, sends a snapshot request, and renders whatever the hub says via a docking shell hosting widget panels (lib/widgets/: session rail, agent console, diff viewer, model manager, terminal, status bar, widget store, clock).
  • RPC child sessions: each agent conversation is a pi --mode rpc --no-extensions --no-skills subprocess with its own session file, spawned per model/thinking choice.

Bus protocol

extensions/pif-shared.ts defines protocol version 1 envelopes: {v, id, ts, channel, type, payload}. Channels are namespaced <area>/<topic> with four dispatch areas — session/, widget/, store/, shell/ — plus a models/ area handled by the hub's model actions (list/save/refresh against ~/.pi/agent/models.json). Transport details verified in source:

  • WebSocket endpoint path is /pif on ws://127.0.0.1:<port> (default port 31415); a minimal hand-rolled WS framing layer handles peers without external dependencies.
  • Token auth is mandatory: the hub generates a random token per launch (or honors PIF_TOKEN), writes it to .pi/pif/token mode 0600, and validates the query-parameter token with a constant-time comparison. Browser origins must be allowlisted via PIF_ALLOWED_ORIGINS; the Dart client sends no Origin header and is unaffected.
  • A Unix control socket at .pi/pif/control.sock accepts newline-delimited JSON-RPC-style method calls for local CLI control.
  • In dev mode the hub launches the shell via flutter run --machine -d macos and speaks the Flutter daemon protocol (attach/restart/stop); the standalone .app connects instead of being supervised.

Widget contract

Widgets are declared by a widget.yaml manifest inside pif/lib/widgets/<id>/ (installed/enabled sources) or pif/catalog/<id>/ (available but uninstalled). Manifest fields include id, name, version, description, slot, core, tags, and dart_dependencies. The hub scans manifests, tracks installed/enabled sets in .pi/pif/registry.json, generates lib/widget_registry.g.dart, and hot-reloads the shell after installs. Layout persists in .pi/pif/layout.json, user preferences in .pi/pif/prefs.json, and a per-launch control.secret for control-socket handshakes.

Session persistence

SessionStore uses node:sqlite when available: a metadata-only sessions table (id, name, model, thinking, cwd, session_file, timestamps) in <workspace>/.pi/pif/sessions.db; otherwise it falls back to sessions.json with the same shape. Transcripts are never stored in the DB: the session .jsonl file is the source of truth, and display history hydrates lazily from it on first selection or resume (hydrateTranscript). Retention keeps the newest 50 sessions per workspace (PIF_SESSION_RETENTION) and deletes older rows with their session files. On stop, live child sessions are upserted; on restart they reload as read-only ended sessions so a reopened project recalls history. The host session is recreated fresh each launch.

Remediation wave 2 (#170) targets exactly these surfaces.

Crash handling, data-integrity around persistence, auth containment on the bus, and performance are the current epic's scope — treat fine-grained claims here as descriptive of commit cc9d1e0f, not as guarantees.

App-builder direction (#152)

Epic #152 extends pif from "IDE shell for pi" toward "agentic applications on the pif foundation": applications composed of hub-managed widgets and sessions, with the #163–#166 tracker panel (repo-synced Kanban board widget fed by gh) as the first concrete precursor. The hub/shell/bus split exists precisely so third-party widgets and apps can ride the same envelope protocol and registry.

07

Council & Comms

Two generations of agent-to-agent messaging ship side by side (both vendored locally from an upstream baseline; extend only in this repo):

coms — local peer-to-peer

extensions/coms.ts: each agent binds a Unix socket (named pipe on Windows) and discovers peers through per-project registry files under ~/.pi/coms/projects/<project>/agents/<name>.json. Tools coms_list/send/get/await, a live pool widget, ping/keepalive cycles, and the /coms command. Messaging is async-by-default: sends land in inboxes and replies are captured when ready; only explicitly synchronous sends block.

council — networked HTTP/SSE hub

extensions/council.ts replaces the substrate with scripts/council-server.ts, a Bun HTTP/SSE hub. Default endpoint 127.0.0.1:48201. The first agent in a project auto-starts the embedded hub when no hub is registered (PI_COUNCIL_AUTOSTART=0 disables this); if port 48201 is busy and the port wasn't pinned, it falls back to an OS-assigned port and records the real URL in ~/.pi/council/projects/<project>/server.json. With no explicit token on loopback the server generates server.secret.json (mode 0600). Registration also mints per-agent session secrets so one bearer token cannot drive another agent's lifecycle operations. Tools mirror coms: council_list/send/get/await plus /council.

Machine-local vs committed boundary.

Everything under .pi/ in a workspace (sessions, tokens, sockets, prefs) and everything under ~/.pi/ is machine-local and git-ignored — .gitignore excludes .pi/, build/, dist/, .githooks/. Committed config such as .mcp.json must reference secrets only through environment interpolation, never literal values. Provider keys belong in your shell environment or keychain, keyed by the names in the table above; this runbook intentionally contains zero key values.

How To Install and Run

Prerequisites

  • pi CLI installed globally (npm i -g @mariozechner/pi-coding-agent).
  • Node.js 20+; Bun for the council hub server; tmux for dashboards/log panes.
  • GitHub CLI (gh) authenticated — used for issue publishing and github-tools.ts auth.
  • Flutter on PATH for any pif work (dev run, global install, or .app build).

Extension install into pi config

Per README.md §Installation: clone the repo, then symlink extensions, agents, and bin entries into ~/.pi-init (where pi loads from), install @mariozechner/pi-tui beside them, and add shell aliases (pi-req, pi-dev, pi-blueprint, pi-council, pi-dash, pi-web). Alternatively load a single extension directly:

pi -ne -e ./extensions/req-qa.ts -e ./extensions/theme-cycler.ts     # requirements
pi -ne -e ./extensions/dev-pipeline.ts -e ./extensions/theme-cycler.ts
pi --no-extensions -e ./extensions/council.ts                        # council client

/pif dev run

With pif.ts loaded, type /pif in a pi session: the hub starts on 127.0.0.1:31415, writes the token file, and spawns flutter run --machine -d macos against the workspace-local pif/ app (or the global copy). /pif-status reports health; /pif-stop tears down hub, shell, and children. Manual shell-only run against an existing hub: PIF_PORT=31415 PIF_WORKSPACE="$PWD" flutter run -d macos.

Global install — scripts/install-pif.sh

Requires flutter on PATH. Installs the Flutter shell to ~/.pi/pif/app/ (backing up any existing install first) and the hub extension to ~/.pi/agent/extensions/pif.ts + pif-shared.ts, then runs flutter pub get. Afterward, run pi in any project and type /pif — widget installs and layout persist per-project in that project's .pi/pif/.

Standalone .app — scripts/build-pif-app.sh

Builds a fully self-contained macOS application (roughly 290 MB):

  1. flutter build macos --release for the native binary.
  2. Bundles the machine's Node.js binary and the installed pi CLI package (dist/cli.js required; override discovery with PI_PKG_DIR).
  3. Copies pif.ts + pif-shared.ts and the Flutter app sources (for widget scanning).
  4. Ad-hoc re-signs the bundle (entitlements preserved) because inserted resources invalidate the release seal on Apple Silicon.
./scripts/build-pif-app.sh            # produces build/pif.app
ditto build/pif.app /Applications/pif.app
open /Applications/pif.app

Bundled layout inside the app:

pif.app/Contents/
  MacOS/pif              ← Flutter native binary
  Resources/
    pi/node              ← Node.js runtime
    pi/cli/              ← pi CLI package
    pi/extensions/       ← pif.ts + pif-shared.ts
    app/                 ← Flutter app source (widget scanning)

On launch the app shows a project picker; selecting a folder spawns pi with PIF_AUTOSTART=1 PIF_NO_FLUTTER=1 so the extension auto-starts the hub and the app connects via the WebSocket bus. If a hub from a terminal session is already running, the app attaches to it directly.
