## What was done

The hub now parses `pif_app/app.yaml` (settled schema: id/name/version/home/pages/template/dependencies) with actionable validation, surfaces the manifest in the snapshot as `app` — **arming the shell's app runtime mode for any project that declares one** — and ships the `pif_app_*` tool surface: `pif_app_init` (scaffolds manifest + Home page, optional `--template mercury` pins the template's layers into `pif_app/template/`), `pif_app_page_add`, `pif_app_widget_add`, `pif_app_home_set`, `pif_app_list`, and `pif_app_build` (registered stub pointing at #159). Repo-shipped templates mirror into the global catalog at hub start. New integration test: real hub boots → init → template pinned → home through the real analyzer gate → page added → manifest live in the snapshot.

## Decisions

- `pif_app` is a **package** (own pubspec: flutter + path dep on the app) — the analyzer resolves project widgets through it, per the #155 layered-sources convention. Init scaffolds it and runs pub get before the install gate.
- Page/widget ids are snake_case (widget-id rule); the app manifest id is kebab.
- Template resolution order: project pinned copy → global catalog → app-bundled templates.
- Writes stay inside `pif_app/` + the global catalog; the app source is never touched by init.
- Cross-lane fix: the hub's widget.yaml validator didn't know the `page` slot #156 added — the shell accepted pages the hub rejected. Validator extended; the integration test caught it.

## Lessons

- Cross-lane contracts need cross-lane tests: #156 (Dart slots) and the hub validator drifted until one integration run joined them.
- When a test points PIF_APP_DIR at the repo's real app source, registry writes land in the repo — snapshot and restore repo state in t.after.
